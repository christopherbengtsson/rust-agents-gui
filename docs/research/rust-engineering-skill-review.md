# Rust engineering skill review

2026-11-12. Question: does the repository's curated `rust-engineering` skill omit useful guidance from the linked upstream collection when assessed against the **whole of `docs/MVP.md`**, including intended capabilities not yet implemented?

**Assessment:** keep and extend the curated skill. Its domain, recovery, async, unsafe, and logging guidance is a good baseline, but the full MVP warrants explicit durability-aware I/O guidance in addition to numeric boundary rules and synchronous resource lifetimes. Boundary-contract documentation is a lower-priority option. Most other upstream omissions do not create a material gap; several upstream examples would introduce incorrect guidance if copied.

This is a static assessment of instructions, not qualification of agent behavior or application correctness. Recommendations below are review inferences; language/API behavior is identified separately and sourced.

## Ranked additions

### 1. Require explicit fallible persistence completion

**Material for the intended MVP, even before storage exists.** Typed persistence errors and general failure accounting are covered ([types:37–48](../../.agents/skills/rust-engineering/references/types-and-errors.md#L37)); Rust I/O completion pitfalls are not. The full contract includes durable action intent, SQLite metadata, transcript/attachment files, archive snapshots, restoration, and visible flush failures ([MVP:29–36,52–65](../MVP.md#L29)). Upstream's [I/O buffering](https://github.com/leonardomso/rust-skills/blob/fd2a861ab0406a4ac536a55274d14ea6fd1ca9c9/rules/perf-io-buffering.md) and [discarded-error guidance](https://github.com/leonardomso/rust-skills/blob/fd2a861ab0406a4ac536a55274d14ea6fd1ca9c9/rules/anti-empty-catch.md) supply useful parts, but do not establish a storage design.

Add a small reference routed for **storage, filesystem/Git output, archive/restore, and shutdown**. It should distinguish successful byte transfer, buffer flush, database commit, and the selected durability guarantee; require explicit fallible finish/flush/commit where the owner needs an outcome; and inspect partial failure across SQLite metadata and separate content files. A database transaction must not be assumed to atomically include external transcript/attachment files or Git effects. Keep recovery decisions in the existing owning modules; follow the MVP's intent-before-effect and archive-preservation order rather than inventing another policy or driver abstraction.

**Documented facts:** Rust's [File documentation at 1.99.1](https://raw.githubusercontent.com/rust-lang/rust/1.99.1/library/std/src/fs.rs) (lines 48–60) says closing errors are ignored by `Drop` and identifies `sync_all` for observing errors. [BufWriter](https://doc.rust-lang.org/std/io/struct.BufWriter.html) also discards flush errors on drop. SQLite documents atomic database transactions and fallible COMMIT ([atomic commit](https://www.sqlite.org/atomiccommit.html), [transactions](https://www.sqlite.org/lang_transaction.html)). **Inference:** none of those mechanisms establishes an atomic commit across this application's database, external content files, Git effects, and provider execution. Explicit error observation and the existing reconciliation policy must bridge those boundaries; neither a Rust buffer flush alone nor automatic destruction proves the required durability.

This addition is API-oriented support for the existing product requirement, not a proposal to mandate a particular journal mode, filesystem technique, database driver, or a new qualification gate. No storage driver is selected in the inspected manifests.

### 2. Make numeric boundary choices explicit

**Useful omission, modest change.** The skill specifies validated inputs and domain-preserving IDs, but discusses integer/handle conversion specifically under unsafe boundaries ([types:5–8,24–33](../../.agents/skills/rust-engineering/references/types-and-errors.md#L5), [unsafe:10–15](../../.agents/skills/rust-engineering/references/unsafe-and-diagnostics.md#L10)). That leaves ordinary safe-code arithmetic implicit. Upstream's [overflow rule](https://github.com/leonardomso/rust-skills/blob/fd2a861ab0406a4ac536a55274d14ea6fd1ca9c9/rules/num-overflow-explicit.md) and [conversion rule](https://github.com/leonardomso/rust-skills/blob/fd2a861ab0406a4ac536a55274d14ea6fd1ca9c9/rules/num-cast-try-from.md) contain a useful principle to retain without importing all their examples.

Suggested addition to `types-and-errors.md`: preserve values across numeric boundaries; use fallible conversions when range/sign can differ, and make overflow behavior explicit where lengths, resource budgets, or sequence/cursor arithmetic can exceed their domain. Checked failure, saturation, or wrapping must match the domain; saturation/wrapping must not silently alias an execution identity or history cursor. Proven bounds can justify ordinary arithmetic.

**Documented facts:** `TryFrom` handles conversions that can fail; `From` has an infallible, value-preserving contract by convention, not a compiler proof for arbitrary user implementations ([TryFrom](https://doc.rust-lang.org/std/convert/trait.TryFrom.html), [From](https://doc.rust-lang.org/std/convert/trait.From.html#when-to-implement-from)). Overflow checks depend on build configuration; debug/release defaults are not a recovery policy ([Cargo profiles](https://doc.rust-lang.org/cargo/reference/profiles.html#overflow-checks)). Checked arithmetic provides a failure result ([u64::checked_add](https://doc.rust-lang.org/std/primitive.u64.html#method.checked_add)).

**Repository relevance, not a defect finding:** history already has a `u64` revision ([core:21–25](../../crates/core/src/lib.rs#L21)); framing combines lengths and deadlines ([connection:280–317](../../crates/core/src/connection.rs#L280)). Current bounds may establish those operations' safety, and the current revision is fixed. The recommendation becomes especially useful as history/event cursors and resource accounting grow under [MVP:59–65](../MVP.md#L59). It does not justify rewriting every addition or cast.

### 3. Cover synchronous resource lifetimes alongside async cleanup

**Useful omission/routing refinement.** The reference contains strong task cleanup guidance but explicitly applies its patterns when async execution is selected ([async:1–4,39–50](../../.agents/skills/rust-engineering/references/async-lifecycle.md#L1)). The main skill covers value transfer, not the lifetime/order of guards protecting OS resources ([skill:25–41](../../.agents/skills/rust-engineering/SKILL.md#L25)). Current source uses a retained file lock and ordinary threads ([supervisor owner:112–121](../../crates/core/src/supervisor.rs#L112), [thread admission:24–38](../../crates/supervisor/src/main.rs#L24), [child waiter:147–161](../../crates/core/src/connection.rs#L147)).

Suggested small main-skill paragraph, or a reference routed for **synchronous I/O, threads, resource guards, or shutdown**: keep guards alive through all work they authorize; account for their destruction order; use RAII for infallible release, with explicit completion methods when cleanup can fail or block and its outcome matters. Assign ownership to spawned thread completion and process wait/stop outcomes. Intentional detachment needs a lifecycle rationale; it is not automatically a defect.

**Documented facts:** struct fields drop in declaration order, locals in reverse order ([Rust destructors](https://doc.rust-lang.org/reference/destructors.html)). Dropping a thread handle detaches rather than joins ([JoinHandle](https://doc.rust-lang.org/std/thread/struct.JoinHandle.html)); dropping `std::process::Child` neither stops nor waits for the child ([Child](https://doc.rust-lang.org/std/process/struct.Child.html)). These facts were also checked in installed Rust 1.99.1 source. Upstream's [drop-order rule](https://github.com/leonardomso/rust-skills/blob/fd2a861ab0406a4ac536a55274d14ea6fd1ca9c9/rules/mem-drop-order.md) supplies the core idea, but its local example releases a guard before the transaction it says the guard must protect; do not copy that example. The product's required stop/durability evidence remains owned by [MVP:61–65](../MVP.md#L61), not by destructor mechanics.

### 4. Optionally document consequential boundary contracts

The skill requires `# Safety` documentation but has no equivalent prompt for recoverable errors, blocking, or partial effects ([unsafe:5–8](../../.agents/skills/rust-engineering/references/unsafe-and-diagnostics.md#L5)). A short instruction to document those caller-relevant facts when changing an owning-module boundary would help future clients. This is lower priority: current completion guidance already asks reviewers to account for failure/cancellation/stale state ([skill:43–48](../../.agents/skills/rust-engineering/SKILL.md#L43)).

The [Rust API Guidelines C-FAILURE](https://rust-lang.github.io/api-guidelines/documentation.html#function-docs-include-error-panic-and-safety-considerations-c-failure) and upstream [error docs](https://github.com/leonardomso/rust-skills/blob/fd2a861ab0406a4ac536a55274d14ea6fd1ca9c9/rules/doc-errors-section.md) support documenting error conditions. Do not turn this into mandatory examples for every public item, a documentation percentage target, or another verification gate.

## Adequate coverage and existing policy

- **Ownership and dependency seams:** borrowed views, intentional ownership/`Arc` snapshots, failure-safe `take`/replacement, and deliberate generics/trait objects are explicit ([skill:25–41](../../.agents/skills/rust-engineering/SKILL.md#L25)). This preserves controllable dependencies without speculative frameworks.
- **Execution types, inputs, errors, Serde:** distinct identities, enums/exhaustive policy decisions, representable uncertainty, validation during deserialization, authority revalidation, typed decision errors, source chains, and invariant-only `expect` are explicit ([types:5–48](../../.agents/skills/rust-engineering/references/types-and-errors.md#L5)). Provider compatibility and fixture provenance are additionally owned by [AGENTS.md:16](../../AGENTS.md#L16). Missing recipes for every Serde attribute are not missing schema policy.
- **Async lifecycle:** count and byte limits, in-flight budgets, overload/closed-receiver meaning, broadcast gap recovery, blocking work, lock-scope tradeoffs, revalidation after unlocking, cancellation/partial progress, joins, and process cleanup are explicit ([async:6–50](../../.agents/skills/rust-engineering/references/async-lifecycle.md#L6)). Installed Tokio 1.54.1 documentation confirms async mutexes are designed to span awaits, and started blocking jobs cannot be aborted; these are important refinements to upstream simplifications. See the version-evidence note below.
- **Unsafe and diagnostics:** full wrapper preconditions, OS ownership, safety comments, structured identities, subscriber ownership, sensitive formatting, and transcript/log separation are covered ([unsafe:5–34](../../.agents/skills/rust-engineering/references/unsafe-and-diagnostics.md#L5)). No current manual `Send`/`Sync` implementation or custom raw-memory abstraction was found in the sampled code; a specific auto-trait rule can wait for that task.
- **Testing/build policy:** deterministic owning-module decisions, typed doubles, controlled time, no new integration tests/generic mocks, separate native qualification, isolated targets, provenance, and proportional gates already live in [verification:11–85](../agents/verification.md#L11). Clippy and formatting scripts already exist ([package scripts:16–19](../../package.json#L16)); their presence is not a claim they passed or that the current broad `test` script is the policy-approved unit gate. Duplicating these policies inside the skill risks divergence.
