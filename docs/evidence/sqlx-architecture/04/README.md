## Implementation and ownership

Core opens SQLx once and passes a clone of that owner to async provider startup. Workspace/provider consumers share its writer/read-only pools. Removed synchronous provider persistence traits, provider store opens and database-only blocking dispatch. Existing incumbent workspace dispatch was already async at 03. No SQL/pool/transaction escapes, per-request runtime, rusqlite bridge, second application storage owner or legacy reader was introduced.

Provider-owned retained workers commit exact selection/login intent before execution. Metadata records provider, configuration target, original revision, credential scope, executable, operation/path and action/attempt identity. A unique pending-scope index protects both action kinds. Selection intent and the validated saved preference are separate: invalid selections never replace the latter. Same-ID/payload is idempotent in storage; mismatch/cross-kind identity reuse rejects; late completion cannot replace a later preference or scope fence. Provider code owns retry/reconciliation, not storage.

Async persistence revalidates scope/target/action and fencing around waits, retains original structured storage faults separately from presentation strings, and exposes them in drain even after later success. Status/cancel do not wait for SQLx acquisition. The existing provider reaper consumes outcomes/panics after requester loss. No root/Tauri operation-result ledger was added. Quit fences admission, transfers/settles owned domain work, closes storage, then permits lease release. A selection delayed in storage settles without effects after Quit. Unconfirmed process cleanup stays fenced after late readiness/login evidence.

Current metadata schema is **4**, initialized directly with no migration/retired-build fallback. Saved selection and pending intent restore from shared settled snapshots. An interrupted attempt remains exact and fenced; status, reconciliation, mount/reconnect and refresh do not replay it. Completed setup evidence remains ephemeral and is freshly verified by the existing journey; app metadata stores no credentials or native login URL.
