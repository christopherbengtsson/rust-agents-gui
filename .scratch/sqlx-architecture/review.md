# Independent architecture review

2026-11-16 · Review and research only · source `24390a1e7ba108ca88704fbf73deac92915d3ab6` plus the pre-existing working-tree documents.

**Assessment: retain the selected direction, amend the mechanisms before treating this as an implementation specification.** Tauri hosting and direct Rust SQLx can delete substantial infrastructure. Concrete domain handles plus one lifetime owner are a sound starting shape. The proposal still leaves important transaction, cross-domain ordering and pressure guarantees without a sufficiently concrete implementation argument, while prescribing several numerical defaults too early.

## Prioritized findings

### 1. High — SQLx default pool reuse does not establish the proposed transaction-cleanup guarantee

**Evidence:** plan §2.3 requires unresolved transaction state to be fenced before reuse. In SQLx 0.9.0, `Transaction::commit(self)` consumes the transaction. An error leaves its drop path to enqueue rollback; drop rollback has no result receiver. The SQLite worker can continue after rollback failure, while ordinary `ping` checks worker responsiveness rather than transaction cleanliness. Default pool return uses that ping. See the exact source chain and conservative remedies in [the reuse research](review-research.md#the-concrete-reuse-hole). Current code deliberately checks autocommit before reads at [storage.rs:224](../../crates/core/src/storage.rs#L224), albeit through a different driver.

**Consequence:** copying normal `pool.begin().await?; … tx.commit().await?` examples does not by itself preserve the committed-read/recovery contract. A later observation could use a connection whose cleanup was not established. This is an upstream failure-path possibility plus a missing design mechanism, not an executed SQLx failure in this application. SQLx remains the selected driver.

**Amendment:** keep this small policy inside storage. Hold an acquired pool connection outside the borrowed transaction scope so a failed write/commit can retire the connection deliberately. Preserve the original error and distinguish failed acknowledgment from absence. Specify a conservative pool-return guard for abnormal drop/panic paths: order pending cleanup, reject unresolved transaction state, and close rather than guessing. Use supported SQLx facilities; do not recreate its transaction worker or build a generic transaction manager. Prove cleanup/replacement ordering with substituted outcomes, then separately qualify actual COMMIT/rollback faults and cancellation. Pool close returning `()` is already correctly qualified by the plan; repeating that caveat does not solve reuse.

### 2. High — Name reservation has a cross-repository conflict that per-repository gates do not cover

**Evidence:** [storage.rs:435](../../crates/core/src/storage.rs#L435) reads all repository folder reservations. [creation.rs:310](../../crates/core/src/workspaces/creation.rs#L310) chooses a folder from that snapshot; [creation.rs:344](../../crates/core/src/workspaces/creation.rs#L344) later persists the chosen folder/name/path. [storage.rs:459](../../crates/core/src/storage.rs#L459) enforces the reservation transaction. Today one workspace worker serializes this sequence. Plan §2.2 proposes concurrency by common Git directory without explicitly assigning this shared managed-folder namespace.

**Consequence:** two unrelated repositories named `app` can both select `app` before either reserves it. A uniqueness constraint prevents duplicate ownership, but one creation can fail unnecessarily instead of choosing a valid variant. This is a concurrency-conversion gap, not a reproduced race in today's single-worker implementation. Within one repository, concurrent name allocation has the analogous read/choose/claim ordering requirement.

**Amendment:** identify reservation as a short shared decision, separate from long Git effects. Prefer a typed atomic candidate-claim storage operation with bounded conflict retry *before* an immutable reservation is committed. Alternatively use a brief workspace-owned reservation gate covering the shared namespace. Neither approach needs a global lock across filesystem inspection or Git execution. After reservation, retries must keep the exact saved location. A writer connection cap of one only serializes individual database operations; it does not serialize the surrounding multi-call decision.

### 3. High — Reserved control admission is insufficient without a provider-stream pressure design

**Evidence:** plan §2.4 reserves control slots and allows multiple conversations in a provider process, but leaves frame limits and the concrete provider backpressure path to chat. The selected readiness cohort is Codex **0.169.0**, source `d32063f…`, per [fixture provenance](../../fixtures/codex-readiness/README.md), rather than the older proof's 0.167.1. In that source, the [stdio transport](https://github.com/openai/codex/blob/d32063f96c2dff1dc96af839b3952abb6acfeda4/codex-rs/app-server-transport/src/transport/stdio.rs#L127) serializes messages through one stdout writer and waits for each write. The [outbound dispatcher](https://github.com/openai/codex/blob/d32063f96c2dff1dc96af839b3952abb6acfeda4/codex-rs/app-server/src/transport.rs#L131) awaits a full non-disconnectable connection queue. Those facts do not establish independent per-conversation flow control.

**Consequence:** a hot conversation can fill a persistence queue; pausing its shared stdout reader can strand control responses, approvals and quieter conversations behind data on the same stream. Sending interrupt through a reserved request lane does not establish receipt or processing. Likewise an OS pipe bound is not a bound on provider RSS. This is a concrete architectural risk requiring qualification, not proof the provider deadlocks.

**Amendment:** before declaring the concurrency handoff complete, select and document provider process-sharing and the overload failure domain. Keep protocol reading/routing separate from bulk persistence waits, with bounded control capacity and a specified saturation transition. Unbounded drain-to-memory is not a solution. When safe selective backpressure is unavailable, stop/fence the affected provider connection, retain its durable prefix and explicit gap, and report which conversations share that failure. Consider separate provider processes for independently controlled sessions where supported; do not mandate a process per historical conversation or add another application owner. Qualify the two shared-workspace conversations plus another workspace with a slow writer, a hot stream, approvals and interrupt on the same actual topology.

### 4. High — Cross-domain lifetime ordering needs an explicit admission/reservation rule

**Evidence:** plan §§2.1/2.4/2.5 assigns workspace-wide admission, conversation execution, provider processes and storage to distinct owners, but gives no concrete ordering for their overlapping decisions. Current [OwnerState](../../crates/core/src/workspaces.rs#L319) plus [registration admission](../../crates/core/src/workspaces.rs#L208) implicitly serializes several checks. [workspace observation](../../crates/core/src/workspaces/creation.rs#L977) uses one `active_workspace` as evidence of running creation, and the worker sets/clears it around physical work. Simply changing this to per-key mutexes is insufficient.

**Consequence:** check-then-start races can admit a send after a workspace fence, or leave shutdown waiting for a task that holds a gate while it awaits another owner. Removing an idle-looking keyed gate while its effect remains alive can permit duplicate authority. Concurrent creation status would also misclassify another active workspace if the sentinel survived.

**Amendment:** use one concrete workspace activity/reservation decision through which a conversation acquires permission to start; lifecycle fencing closes that decision before enumerating/draining affected work. Active records identify action/workspace/conversation and retained physical handle, not one global selected workspace. State the allowed acquisition order and forbid reverse calls while holding an owner gate. Release short admission gates before long effects and before joining tasks; completion applies only against the captured generation/reservation. Keep credential-scope exclusion provider-owned. No generic lock manager or universal activity engine is needed. Add controlled races for admission versus Quit, two same-workspace conversations, stale completion and reservation retirement.

### 5. Medium — Uncapped cardinality is incompatible with the remaining load-all naming path

**Evidence:** [storage.rs:435–452](../../crates/core/src/storage.rs#L435) materializes every repository folder and every saved name for a repository. ADR 0005 makes reservations permanent. [naming.rs:84](../../crates/core/src/workspaces/naming.rs#L84) scans successive name tiers. The catalogue is bounded; retained reservation sets and the number of tiers are not. Plan §2.4 bounds observation pages but does not address this internal write path.

**Consequence:** page limits do not bound allocation cost, startup recovery scans or reservation memory as history grows. This is source-proven unbounded materialization, not a measured latency regression and not a reason to cap saved workspaces.

**Amendment:** replace load-all reservation sets with indexed candidate existence/claim operations or bounded scans with continuations. Keep readable labels and permanent exact reservations. Bound filesystem/Git enumeration separately from saved metadata; expose unavailable/too-large evidence honestly. Audit other startup and pending-action enumeration for the same assumption. Avoid new schema for future workflows; an index or bounded operation for an existing reservation is justified now.

### 6. Medium — The two-pool topology is plausible, but the proposal has not earned its extra lifetime

**Evidence:** plan §2.3 prescribes one writer pool plus two readers. The retained comparison used that topology for both candidates; it did not compare topologies. SQLite permits one writer and concurrent WAL readers; it does not require two pools. SQLx supplies pool acquisition and read-only open options. See [topology research](review-research.md#3-split-pools-are-a-policy-choice-make-readers-actually-read-only).

**Consequence:** two pools add initialization, configuration, health, replacement and closure paths. Without enforced read-only readers, they also provide no mechanical write separation. Conversely, a single unrestricted pool can let output occupy every connection; removing the split without testing would also be unjustified.

**Amendment:** keep topology private and choose the smallest shape that passes the production-path requirement. Candidate A is one small SQLx pool with private write serialization and bounded admission; candidate B is the proposed max-one writer pool plus a read-only reader pool. B earns its cost if it demonstrably preserves history/control access during writes or simplifies query-only enforcement. Initialize WAL/schema through the writable path before readers open; verify effective connection-local settings and avoid trying to change persistent journal mode from read-only readers. No connection-per-workspace/conversation. Exact reader count and timeout are provisional, not architectural acceptance. No new benchmark contest is needed: use bounded storage/desktop qualification of the chosen shape.

### 7. Medium — Resource and batching numbers are hypotheses; simplify their enforcement model

**Evidence:** §§2.4/2.6 specify 64/8/8/2 request/effect slots, 1+2 connections, 1 s acquisition, 64 events/256 KiB/25 ms batches, 16 MiB global output, 4 MiB workspace shares, byte-aware round robin, urgent preference, and 128-page/16 MiB inactive Query retention. Existing [ObservationCoordinator](../../src/lib/observation-coordinator.ts#L28) already owns two physical reads and a 64-entry queue; [Query defaults](../../src/lib/feature-query-cache.ts#L14) use five-minute GC. The comparison's larger-batch diagnostic still rejected hot-workspace output. Neither source establishes these values as a coherent production budget.

**Consequence:** each extra counter/queue/priority lane creates another lifetime to account for. Byte-aware round robin needs an actual deficit/credit rule; one variable-sized batch per workspace is only batch fairness. Borrowing and urgent starvation are named but not specified. A per-workspace minimum does not imply fairness among two conversations sharing that workspace. A database batch already executing cannot be preempted by urgent admission.

**Amendment:** separate three things: required invariants (bounded retained bytes, exact outcomes, control progress, no silent output loss), a short tunable configuration table, and measured acceptance traces. Start with maintained bounded channels, semaphores and count/byte/time-bounded batches. Keep only a small ready-workspace rotation if needed; add deficit scheduling or borrowing machinery only if the declared noisy-neighbour trace justifies it. Use conversation FIFO/ordering inside each workspace and state whether fairness is per workspace or also per active conversation. Token/request FIFO alone cannot supply workspace fairness; [Tokio's semaphore](https://docs.rs/tokio/1.54.1/tokio/sync/struct.Semaphore.html) also documents head-of-line blocking for large permit requests.

Defer the new serialized-byte Query eviction mechanism unless a hard cache bound is deliberately retained as a requirement; time GC alone is not a hard count/byte bound. If a hard bound is wanted now, one small Query-cache-owned inactive-entry count policy is easier to reason about than repeated serialization and a second body index. Preserve freshness generations and pending action identities when evicting; active and obsolete-physical results still need separate accounting. Qualify actual retained heap before claiming a 16 MiB memory guarantee.

**Specific correction:** “reject before transfer” cannot describe all Tauri IPC memory. The [Tauri 2.12.5 command argument implementation](https://github.com/tauri-apps/tauri/blob/tauri-v2.12.5/crates/tauri/src/ipc/command.rs#L68) deserializes arguments from an already received payload. Reject before **core queue/task/effect admission**, bound app-generated inputs before invoke, and account for decoding/IPC copies separately. Do not promise a new custom IPC parser merely to enforce a misleading aggregate figure.

### 8. Medium — Keep the lifetime module deep; do not make it a second domain task manager

**Evidence:** the plan correctly finds [owner release before workspace drop/join](../../crates/supervisor/src/main.rs#L90), [provider/transport-only finish](../../crates/core/src/connection.rs#L1158), and [discarded reply delivery](../../crates/core/src/connection/tasks.rs#L31). Current task ownership lives in both connection tasks and provider tasks; workspaces owns a separate thread. §2.4 recommends retained `JoinSet` outcomes and identity association, but does not say which module continuously polls which set once the socket accept loop disappears.

**Consequence:** replacing `Supervisor` with `CoreOwner` while copying connection task registries and adding another result ledger moves infrastructure. A generic root result enum also leaks domain settlement into composition. `JoinSet<()>` cannot by itself preserve a failed domain result discarded inside its task, and `JoinSet` drop aborts async tasks.

**Amendment:** root owns state lease, admission phase and concrete domain-owner completion handles. Each domain owns its actual operations, continuously reaps results, settles recoverable outcomes and exposes a compact drain report. Root joins domains in dependency order while storage remains open; it does not implement their retries or duplicate their result bodies. A single root set is a viable alternative only if each owned task performs domain settlement before returning and the set's panic-to-domain association is explicit. Use one design, not both registries everywhere. Deadline leaves the same retained shutdown attempt active; retrying Quit observes it. Startup rollback must visit every acquired resource despite earlier errors. Retain the accepted rule that normal success releases the lease last; native crash is recovery, not successful drain.

Include concrete failure replacements: `ConnectionServer::finish` currently skips provider cleanup after a task error; [provider join](../../crates/core/src/runtimes/provider_connection.rs#L598) stops on the first panic; workspace drop discards join failure. Put the retained shutdown coordinator outside the sets it drains and collect all stage failures. Delete whole-app `BeginShutdown`/`FinishShutdown` provider actions when core lifetime takes ownership; providers keep their local stop/join mechanism. Also require any later restart/update path to finish core shutdown before Tauri restart, whose interception differs from ordinary Quit ([lifecycle research](review-research.md#6-tauri-supplies-a-host-runtime-and-exit-interception-not-automatic-domain-drain)).

### 9. Medium — The stages need smaller review surfaces and a pressure gate tied to actual chat

**Evidence:** stage C combines driver/schema replacement, workspace async coordination, provider persistence, diagnostics and outcome retention. D then combines rehosting, contracts, delivery and toolchain deletion. E promises pressure handoff before F implements the output producer and writer policy that matter most. The stage descriptions are dependency-aware but too broad to be session-sized review gates.

**Amendment:** keep A's explicit authority publication first. Within B–D, split review checkpoints by coherent capability: (1) explicit whole-core completion and lease ordering on incumbent host; (2) current-schema SQLx ownership plus transaction quarantine/settled reads; (3) workspace admission/reservation async conversion and bounded naming; (4) provider persistence conversion; (5) native-host composition and direct action/feed slice; (6) delete retired transport/staging and qualify packaging. The exact cutover can combine adjacent checkpoints when a coherent build requires it; do not preserve dual drivers or build a generic legacy-host adapter. Move streamed fairness/batching qualification to F, with E publishing only foundational guarantees actually exercised. F's three-conversation scenario remains mandatory and does not imply a product maximum.

Preserve useful substituted assertions before deleting old orchestration tests. Retired-format fixtures may be retired under the accepted policy; owner exclusion, external protocol matching, intent-before-effect and cleanup assertions need replacements. Keep storage/process qualification separate from application units. No passing test label substitutes for actual Tauri, native process, storage or separately authorized provider evidence.

## Recommended module shapes

These are alternatives to carry into the later design session, not new interfaces or implementation tickets published by this review.

| Module | Recommended shape and seam | Alternative and tradeoff |
| --- | --- | --- |
| Core lifetime | One UI-independent lifetime module with concrete workspace/runtime/storage owners; thin Tauri adapter | One root operation `JoinSet` can work if domain settlement stays inside tasks. Avoid root and domain sets tracking the same physical operation. |
| Workspace activity | Short workspace-owned reservation decision; retained per-operation activity; per-repository Git mutation exclusion; atomic global folder claim | A small serialized workspace coordinator can be simpler initially than a keyed mutex registry. It must dispatch independent effects concurrently, rather than serialize their entire durations. |
| Storage | Domain-shaped operations; private SQLx graph; explicit error quarantine and short consistent read transactions | Split pools versus one bounded pool is an internal choice. Neither pool is a workflow scheduler. Do not expose SQL, connections, transaction objects or arbitrary closure dispatch to callers. |
| Process effects | Shared bounded pipes/wait/signalling mechanics, with finite Git command and provider-protocol adapters | Share mechanisms only where contracts match. A finite command collector and a bidirectional long-lived protocol should not be forced through one universal `run` abstraction. |
| Conversations, later | Exact application/native mappings, turn/action policy and bounded durable event ingestion | Provider process sharing stays inside runtimes; a Claude TypeScript/Bun adapter later owns protocol conversion, never application storage/workflow truth. |

Depth comes from hiding ordering and lifetime facts callers should not reproduce. The deletion test supports removing discovery, socket framing, negotiation and staging. It does **not** support removing workspace identity/recovery, validated observations, the state lease or exact process cleanup merely because they now run in-process. Locality and leverage should improve at the domain interface; a smaller file count is not the goal.

## Qualification gaps versus established findings

Established by source: current load-all naming, direct reopen escaping the test seam, discarded reply results, incomplete successful shutdown path, and specific upstream SQLx cleanup/reuse semantics. The proposed concurrent reservation race, provider head-of-line pressure and cross-domain admission races are design gaps, not reproduced application defects. Numerical capacities and performance benefits are unqualified hypotheses.

For the later implementation, retain four separate cohorts:

1. **Substituted application units:** real domain decisions with controlled storage/process/filesystem/Git outcomes. Include transaction retirement/settled read, duplicate IDs and payload mismatch, global-folder claim conflicts, reservation generation, cancelled waiter, panic attribution, admission versus fence and lease-last shutdown. No new integration-test framework.
2. **Actual storage/process:** fresh private current-build state, effective PRAGMAs and actual engine/WAL fix, open/reopen under the accepted private-directory contract, rollback/COMMIT faults, pool replacement, pinned readers/checkpoints, lease exclusion, descendants and partial startup/quit. Process-crash evidence does not prove power-loss durability or escaped-descendant cleanup.
3. **Actual fixture desktop:** the Tauri-hosted path, direct action/feed, startup/failed startup, WebView replacement, native failure/reopen, Quit during work, saturation with usable controls, packaging and concurrent workspace operations. Preserve earlier supervisor evidence as its cohort.
4. **Separately authorized native provider:** supported source/runtime cohort; two conversations sharing a workspace and another workspace working concurrently; exact routing, approvals, interrupt/cleanup, pressure, retained history and resume. Readiness fixtures reject thread/turn operations and cannot qualify this by relabelling.

This session ran no application tests, builds, benchmarks, providers, authentication or desktop product qualification. Review artifact validation is reported separately. Existing evidence was read, never rewritten. Conductor was not launched; databases, credentials and user history were not inspected. RAT was not inspected. No dependencies were installed or state reset.
