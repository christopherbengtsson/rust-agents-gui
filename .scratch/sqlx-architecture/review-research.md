# Primary-source review of the SQLx architecture plan

2026-11-16 · Research and static review only. This note reviews [the plan](plan.md); it changes no product policy, implementation, ticket or retained evidence.

The selected Tauri-hosted, UI-independent Rust core and direct SQLx direction is technically sound. The most consequential missing detail is **how storage prevents a connection with failed transaction cleanup from returning to ordinary use**. SQLx supplies useful cancellation bookkeeping, but its default SQLite pool health check does not enforce that promise. The plan's general warning about uncertainty needs one concrete storage-owned mechanism.

Other conclusions are less dramatic: split writer/reader pools are a reasonable small design, read-only readers should be explicit, `JoinSet` is suitable when outcomes are consumed continuously, and Tokio can replace pipe polling without replacing application cleanup policy. Exact numerical budgets and fairness algorithms remain proposed settings rather than established production requirements.

## 1. SQLx cancellation is useful bookkeeping, not cancellation of effects

SQLx's SQLite connection owns a blocking worker thread and bounded command/row channels. Dropping a caller cannot retroactively stop a SQLite call already in progress. Row delivery notices a missing consumer between produced results, rather than supplying a universal interrupt of `sqlite3_step`. Async interfaces therefore remove application worker plumbing without converting all physical work into abortable Tokio work. [Connection implementation](https://github.com/transact-rs/sqlx/blob/003b698e99e024f3621b8043a2426fde5b741171/sqlx-sqlite/src/connection/mod.rs#L43), [execution worker](https://github.com/transact-rs/sqlx/blob/003b698e99e024f3621b8043a2426fde5b741171/sqlx-sqlite/src/connection/worker.rs#L163).

The versioned transaction paths establish these narrower facts:

| Boundary | Actual mechanism | Application implication |
| --- | --- | --- |
| Unacknowledged successful `BEGIN` | Worker attempts rollback and exits if that rollback fails. | Maintained cleanup covers this particular cancellation path. |
| Unacknowledged successful `COMMIT` | Worker suppresses the subsequent drop-triggered rollback. | A missing acknowledgment can coexist with committed data. |
| Ordinary transaction drop | Starts rollback; no rollback result is returned to the dropping caller. | Drop is fallback cleanup, not a reported rollback receipt. |
| Failed commit | `commit(self)` returns an error while its still-open transaction is dropped. | The consumed transaction cannot simply be rolled back afterward through that same value. |

The first two mechanisms are in the [worker's transaction branches](https://github.com/transact-rs/sqlx/blob/003b698e99e024f3621b8043a2426fde5b741171/sqlx-sqlite/src/connection/worker.rs#L213); consumption and drop are in [core Transaction](https://github.com/transact-rs/sqlx/blob/003b698e99e024f3621b8043a2426fde5b741171/sqlx-core/src/transaction.rs#L119). SQLite itself documents that a BUSY commit can leave a transaction active, and that some other errors may roll back a statement or the transaction. [SQLite transaction errors](https://www.sqlite.org/lang_transaction.html#implicit_versus_explicit_transactions).

**Recommendation:** retain admitted write tasks independently of IPC receivers and do not race those tasks against request cancellation. A timeout may change the observation returned to the caller; it must not authorize replay or release ownership of unresolved physical work. This preserves the plan's intent-before-effect/reconciliation design without building another driver worker.

### The concrete reuse hole

For a dropped transaction, the SQLite transaction manager discards any error while enqueueing rollback. The worker's rollback command has no reply sender in this path; a failed rollback does not decrement its transaction depth. In contrast with cancelled-BEGIN cleanup, this branch does not terminate the worker. The SQLite `Ping` command just acknowledges receipt. [SQLite transaction manager](https://github.com/transact-rs/sqlx/blob/003b698e99e024f3621b8043a2426fde5b741171/sqlx-sqlite/src/transaction.rs#L26), [rollback and ping branches](https://github.com/transact-rs/sqlx/blob/003b698e99e024f3621b8043a2426fde5b741171/sqlx-sqlite/src/connection/worker.rs#L285).

The pool return path invokes `after_release`, then pings before putting the connection into the idle queue. Its default ping therefore orders earlier worker commands but does not prove that their rollback succeeded. This is a **source-derived failure path**, not a reproduced production bug: if rollback fails and the worker remains responsive, the default pool path can return a connection whose tracked transaction remains open. [Pool return implementation](https://github.com/transact-rs/sqlx/blob/003b698e99e024f3621b8043a2426fde5b741171/sqlx-core/src/pool/connection.rs#L272).

**Minimum concrete amendment:** keep the acquired `PoolConnection` outside a transaction borrowed from it. On a statement/commit error, retain the original failure, let the transaction scope finish, and explicitly close that acquired connection before replacement/reconciliation. Do not let the ordinary error path return it to idle first. `PoolConnection::close(self)` supplies a fallible library-owned retirement path. [Acquired connection close](https://github.com/transact-rs/sqlx/blob/003b698e99e024f3621b8043a2426fde5b741171/sqlx-core/src/pool/connection.rs#L78).

As a conservative panic/drop fallback, `after_release` can await a worker ping and then reject a connection whose `Connection::is_in_transaction()` remains true. Awaiting the ping first matters: reading the depth before queued rollback runs can reject a successfully cleaning-up connection. SQLx documents that this predicate may overcount automatic rollback, so retirement is conservative, not an exact SQLite-state diagnosis. `after_release` rejection closes through the maintained pool; it is not itself a durable failure record. Domain/task panic handling must separately fence and retain the affected action's uncertainty. [Hook contract](https://github.com/transact-rs/sqlx/blob/003b698e99e024f3621b8043a2426fde5b741171/sqlx-core/src/pool/options.rs#L446), [transaction-state predicate](https://github.com/transact-rs/sqlx/blob/003b698e99e024f3621b8043a2426fde5b741171/sqlx-core/src/connection.rs#L71).

This is less machinery than a public transaction coordinator, custom connection pool, or custom rollback protocol. It belongs inside typed storage operations. A returned close error and the original operation error remain distinct; closing cannot establish whether an earlier unacknowledged commit happened.

## 2. What explicit close does and does not establish

`SqliteConnection::close` optionally runs optimize-on-close, requests shutdown, drops its own handle, then awaits the worker acknowledgment. The worker drops connection references before acknowledging. The source has no caller-owned OS-thread join handle. The SQLite handle destructor uses `sqlite3_close` and panics on an unexpected non-OK result. Thus describing the close API as fallible is accurate; describing it as a structured inventory of every SQLite-close failure would be inaccurate. [Connection close](https://github.com/transact-rs/sqlx/blob/003b698e99e024f3621b8043a2426fde5b741171/sqlx-sqlite/src/connection/mod.rs#L220), [handle destructor](https://github.com/transact-rs/sqlx/blob/003b698e99e024f3621b8043a2426fde5b741171/sqlx-sqlite/src/connection/handle.rs#L139).

`Pool::close().await` closes admission and waits for checked-out connections; its return is `()`. Individual raw-close results in pool shutdown are discarded. The plan already acknowledges this limitation, so it is **not a new defect**. The amendment above addresses the earlier error/reuse boundary rather than asking pool shutdown to recover lost errors. [Pool public contract](https://github.com/transact-rs/sqlx/blob/003b698e99e024f3621b8043a2426fde5b741171/sqlx-core/src/pool/mod.rs#L420), [pool close implementation](https://github.com/transact-rs/sqlx/blob/003b698e99e024f3621b8043a2426fde5b741171/sqlx-core/src/pool/inner.rs#L96).

Pool acquisition cancellation may drop an already acquired/new connection, as documented. Connection replacement must therefore rerun establishment configuration and validation; disabling timed connection churn does not eliminate legitimate reopen paths. Keep the accepted same-user replacement-race limitation explicit. [Acquisition cancellation](https://github.com/transact-rs/sqlx/blob/003b698e99e024f3621b8043a2426fde5b741171/sqlx-core/src/pool/mod.rs#L340).

## 3. Split pools are a policy choice; make readers actually read-only

SQLite permits multiple readers and one writer. WAL enables overlap, not multiple simultaneous writers. SQLx's pool fairly queues acquisition; that fairness is among callers waiting for a connection, not workspaces, operation classes or bytes. [SQLite isolation](https://www.sqlite.org/isolation.html), [SQLx pool contract](https://github.com/transact-rs/sqlx/blob/003b698e99e024f3621b8043a2426fde5b741171/sqlx-core/src/pool/mod.rs#L95).

| Topology | Simplicity/behavior tradeoff |
| --- | --- |
| One bounded pool | Fewest pool configurations; long reads can occupy every connection. A separate writer gate still does not reserve a physical writer connection. |
| One single-connection pool | Simple serialization and cancellation boundary; eliminates concurrent read/write execution even in WAL. Whether this meets responsiveness is a production question. |
| One single-writer pool plus a small reader pool | Explicit writer capacity and different reader opening flags using maintained APIs; two configurations and two close barriers, without a custom acquisition scheduler. |

**Recommendation:** the plan's split topology is defensible if reserved write progress and read-only access are intended requirements. Do not justify it merely by SQLite's one-writer rule or by Conductor. Keep both pools private and share establishment logic. Two readers are a starting setting, not an architectural constant; a simpler pool remains a valid alternative if qualification shows no need for reservation.

The plan currently names a reader pool without specifying its access mode. Use `SqliteConnectOptions::read_only(true)` and no creation on reader connections, rather than relying only on callers choosing SELECT. SQLx translates that to `SQLITE_OPEN_READONLY`. Initialize schema/WAL through the writer before opening readers; inherit the persistent WAL mode and verify it, avoiding unnecessary journal-mode transitions on every reader open. [SQLx opening flags](https://github.com/transact-rs/sqlx/blob/003b698e99e024f3621b8043a2426fde5b741171/sqlx-sqlite/src/connection/establish.rs#L60), [journal-mode options](https://github.com/transact-rs/sqlx/blob/003b698e99e024f3621b8043a2426fde5b741171/sqlx-sqlite/src/options/mod.rs#L260).

Do not set `immutable(true)` for a live writer's database: SQLx documents that it disables locking/change detection and can yield incorrect results if the file changes. `query_only` is a useful optional guard, but SQLite explicitly does not promise it prevents every disk-affecting operation. Read-only WAL opening also has WAL/SHM existence/creation conditions to qualify. [Immutable option](https://github.com/transact-rs/sqlx/blob/003b698e99e024f3621b8043a2426fde5b741171/sqlx-sqlite/src/options/mod.rs#L391), [SQLite query_only](https://www.sqlite.org/pragma.html#pragma_query_only), [read-only WAL](https://www.sqlite.org/wal.html#read_only_databases).

## 4. Busy handling and checkpoints cannot supply a latency promise

A busy timeout accumulates sleeps in SQLite's busy handler; it is not a total operation deadline. A 1-second pool-acquisition timeout covers another boundary. Some lock cases return BUSY without invoking the handler. These settings do not establish that an admitted write completes within either interval. [Busy timeout](https://www.sqlite.org/c3ref/busy_timeout.html), [checkpoint locking exceptions](https://www.sqlite.org/c3ref/wal_checkpoint_v2.html).

WAL autocheckpoint is normally attempted by the transaction whose commit crosses its page threshold. A long reader can prevent complete checkpoint progress, so 1,000 pages is not a WAL-size cap. Short scoped read transactions and bounded history materialization are useful before adding a checkpoint service. [SQLite checkpoint scheduling and growth](https://www.sqlite.org/wal.html#automatic_checkpoint).

PASSIVE checkpoints do not wait for readers/writers and may finish incompletely. FULL/RESTART/TRUNCATE have stronger waits and writer-lock consequences. Even PASSIVE may perform disk work; cancelling its awaiting future does not prove that work ended. **Recommendation:** retain automatic checkpointing initially, observe returned progress when explicitly probing/checkpointing, and introduce dedicated scheduling only for a demonstrated production problem. A mandatory truncation at every successful shutdown would create an unnecessary stronger guarantee. [Checkpoint modes](https://www.sqlite.org/c3ref/wal_checkpoint_v2.html).

## 5. Use JoinSet deliberately; TaskTracker is an alternative, not another mandatory layer

`JoinSet` retains completed results until joined, aborts its tasks when dropped, and offers cancel-safe `join_next_with_id`; errors expose a task ID. `shutdown()` calls `abort_all` and joins cancellation, while `join_all()` panics on a task join error and cancels remaining work. Neither convenience operation matches collect-all-errors graceful durability drain. [Tokio 1.54.1 JoinSet](https://github.com/tokio-rs/tokio/blob/tokio-1.54.1/tokio/src/task/join_set.rs#L300).

TaskTracker immediately frees completed task storage and provides a completion barrier after closure and emptiness; dropping it does not abort tasks. Its `close()` explicitly permits further spawning. It does not replace outcome handling or the core's admission fence. [Tokio-util 0.7.20 tracker](https://github.com/tokio-rs/tokio/blob/tokio-util-0.7.20/tokio-util/src/task/task_tracker.rs#L17).

**Recommendation:** keep the plan's continuously reaped JoinSet for operations whose outcomes/panics must settle. Use one small task-ID-to-domain-identity association for panic attribution. Avoid adopting both collections for every task or building a second result registry merely to use TaskTracker. A spawned task's completion proves its future/destructor ended, not arbitrary asynchronous effects initiated in destructors. Started `spawn_blocking` work and SQLx worker work need their actual effect barriers. [Tokio task completion](https://github.com/tokio-rs/tokio/blob/tokio-1.54.1/tokio/src/runtime/task/join.rs#L11), [blocking cancellation contract](https://docs.rs/tokio/1.54.1/tokio/task/fn.spawn_blocking.html).

## 6. Tauri supplies a host runtime and exit interception, not automatic domain drain

Tauri 2.12.5 exposes one singleton Tokio runtime and recommends ordinary async command handlers. The core can use Tokio types/handles without depending on Tauri or constructing a runtime per request. This supports the selected process architecture. [Tauri async runtime](https://github.com/tauri-apps/tauri/blob/tauri-v2.12.5/crates/tauri/src/async_runtime.rs#L3).

The run callback is synchronous. `ExitRequested` permits synchronous `prevent_exit`, after which a retained async shutdown owner can drain work and request exit once allowed. `cleanup_before_exit` clears Tauri resources; it does not await application tasks. Tauri restart is a separate edge: `prevent_exit` is ignored for the restart code, and a main-thread `restart()` may bypass event delivery. **Recommendation:** route any later restart/update path through completed core shutdown before invoking the framework restart operation. Repeated ordinary exit requests must observe one shutdown owner. [Tauri 2.12.5 lifecycle source](https://github.com/tauri-apps/tauri/blob/tauri-v2.12.5/crates/tauri/src/app.rs#L79).

## 7. Maintained process libraries: useful mechanisms with narrower guarantees

Tokio already supplies asynchronous child pipes, waits, process groups and direct kill. Its docs distinguish signal submission from waiting/reaping; kill-on-drop only gives best-effort background reaping, and `wait_with_output` accumulates output into vectors. Replace nonblocking read/sleep plumbing with these maintained primitives while preserving bounded incremental draining and an explicit owned-process completion result. [Tokio process implementation](https://github.com/tokio-rs/tokio/blob/tokio-1.54.1/tokio/src/process/mod.rs#L630), [output collection](https://github.com/tokio-rs/tokio/blob/tokio-1.54.1/tokio/src/process/mod.rs#L1430).

process-wrap 10.0.1 supplies composable group/session and Windows job-object wrappers. Its published Unix Tokio implementation still awaits/reaps the leader first, then uses negative-PGID `waitpid` and treats ECHILD as completion. It can use `spawn_blocking` for remaining group wait. That is a reapable-child result, not a universal assertion that no live member remains in a macOS process group; the repository currently preserves unreaped-leader authority while evaluating group quiescence. Apple's archived contract explicitly allows ECHILD when a group has no member that is a child of the caller. The newer release therefore does not by itself remove the reason for the plan's limited recommendation. [Published group implementation](https://github.com/watchexec/process-wrap/blob/ca45003a831ac125e6673b8759430e5ef33cc1db/src/tokio/process_group.rs#L118), [Apple waitpid contract](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/waitpid.2.html), [current local cleanup boundary](../../crates/core/src/runtimes/codex/process.rs#L231).

The Tokio `KillOnDrop` wrapper sets the underlying Command's option; no separate Unix descendant containment follows from its name. `command-group`'s maintainer explicitly names process-wrap as successor and says no further work will be done on command-group. **Recommendation:** update the assessed cohort in a later amendment, retain Tokio plus one deep process-effect owner now, and adopt process-wrap only for an exercised portability/mechanism benefit. Do not replace macOS cleanup evidence with group-wait success or claim native-crash containment. [KillOnDrop source](https://github.com/watchexec/process-wrap/blob/ca45003a831ac125e6673b8759430e5ef33cc1db/src/tokio/kill_on_drop.rs#L15), [maintainer notice](https://github.com/watchexec/command-group/blob/main/README.md).

## 8. Precision to defer and concrete adoption gates

The existing async harness used identical application admission and scheduling on both stacks. Its heavy workloads rejected offered events; its later 64-event diagnostic motivates exploration of grouping. Neither establishes the exact production settings `64 events / 256 KiB / 25 ms`, `16 MiB` globally, `4 MiB` per workspace, reader count two, or all of the proposed control reserves. The plan labels these starting defaults, which is appropriate. They should not become mandatory architectural contracts before chat payloads and actual provider backpressure behavior are known. [Retained comparison and limitations](../../docs/research/storage-async-architecture-comparison.md#measured-comparison).

Byte-aware round robin, borrowing unused workspace shares, urgent rechecks and starvation prevention together define a nontrivial scheduler. SQLx FIFO acquisition supplies none of those semantics. **Recommendation:** specify required outcomes first—bounded admitted bytes, visible overload, durable-prefix preservation, usable stop/status and progress for quiet workspaces—and add the smallest private writer policy that demonstrates them. Count/byte/time batch triggers are useful candidates; a universal scheduler and preallocated per-workspace queues are unnecessary. Quantify queue, driver-row and result/decode copies separately; row-count limits alone do not bound arbitrary row bytes. [SQLx buffer options](https://github.com/transact-rs/sqlx/blob/003b698e99e024f3621b8043a2426fde5b741171/sqlx-sqlite/src/options/mod.rs#L438).

Before calling the design qualified, later work should establish:

1. The explicit failed-write connection retirement/return guard, original-error retention, and action reconciliation described above; pool ping/close alone is insufficient.
2. Effective read-only reader opening, initialization/replacement settings, and accepted private-state checks in the actual graph, with its engine/version recorded.
3. Request disappearance and task panic behavior without losing action identity, prematurely claiming physical completion, or releasing the state lease early.
4. Actual Tauri Quit/startup races, bounded reads and persistence pressure in the agreed concurrent scenario: two chats sharing a workspace while another runs elsewhere. These counts are acceptance observations, never product caps.
5. Separate unit evidence with substituted effects, real storage/native lifecycle qualification, fixture-desktop evidence, and separately authorized native-provider evidence. No extra framework or driver contest is required to answer these questions.

The future gh CLI and TypeScript/Bun Claude bridge remain adapters to the same Rust action/authority/lifetime semantics. They do not justify adding a job framework, generic workflow engine or second storage owner in this refactor.
